# T8.2 — Allocation and contention report

Captured 2026-09-25 on the development machine (12 logical cores, live desktop
session — background load noted where it matters). Raw profiles live
alongside this report: `heap.prof`, `block.prof`, `mutex.prof`.

## A note on what could and could not be measured

Hypotheses were written before any of the data below was looked at, per the
task's own instruction; the write-up below states each hypothesis first and
then what the data showed.

**CPU profiling could not be captured in this environment.** Both capture
paths were tried:

* `curl .../debug/pprof/profile?seconds=N` against the live server under
  `test/bench/loadgen` write load — the server is reliably `SIGKILL`ed within
  about a second of the profile starting, reproduced 8/8 times across a range
  of durations (1s–15s) and client counts (5–50).
* `go test ./test/stress -cpuprofile=...` — killed in 7ms, before the test
  even ran, with no load involved at all.

Isolating the variable: the server survives indefinitely under the same load
with *no* CPU profile requested, and heap/mutex/block profiles against the
same loaded server succeed without incident. The failure is specific to
`runtime.StartCPUProfile`'s `SIGPROF`/`setitimer` mechanism in this sandboxed
execution environment, not to memory pressure, not to load, and not to the
server's own code — `go test -cpuprofile` fails identically for a trivial
test with no server involved. This is an environment limitation, not a
project defect, and no CPU flamegraph is fabricated to paper over it. The
**top CPU consumers section below is therefore a hypothesis ranked from code
inspection of the hot path, explicitly not a measurement** — flagged
accordingly, and it is the one section of this report that does not meet the
task's "profile first" bar. Re-running `test/bench/profile-durable.sh` on an
unrestricted machine is the identified next step.

Heap/allocation and mutex/block profiles were captured successfully and are
real measurements.

## Top 5 CPU consumers (hypothesis only — not measured, see above)

Ranked by static reasoning over the request path
(`internal/server/conn.go` → `internal/resp` → `internal/engine`), heaviest
first:

1. **RESP parsing (`internal/resp.Reader.readArray`/`readBulk`)** — every
   command re-parses its argument array and each bulk string from the
   connection's `bufio.Reader` byte-by-byte-ish via length-prefixed reads;
   this runs on every single command with no shortcut for small commands.
   Hypothesis: dominant CPU consumer under any write-heavy workload, because
   it runs unconditionally before the command even reaches the engine.
2. **`memtable.SkipList.Insert`** — probabilistic level generation plus
   pointer-chasing comparisons on every `Put`; comparisons walk the key
   bytes, and skip lists are asymptotically log n but with a larger constant
   than a plain slice for small memtables.
3. **`wal.Batch.Encode`** — every acknowledged write is serialized into the
   WAL's byte-exact record format before the fsync; this is unavoidable work
   per the durability invariant, but the encode path allocates and copies
   the key/value into the batch buffer rather than encoding in place.
4. **`sstable.BlockBuilder.Add`** during flush — prefix-shared key encoding
   plus checksum computation over each block; expected to be visible only
   during flush/compaction windows, not steady-state serving.
5. **Bloom filter hashing (`bloom.Builder.Add`)** — per-key hashing during
   flush; expected to be a minor contributor relative to 1–4 given T5.1's
   filter is sized for cost, but included because it runs on every key in
   every flushed table.

**Proposed fix for each, to be tested in T8.3:** (1) avoid re-slicing/copying
in `readBulk` by returning a view into the connection's read buffer where the
value doesn't outlive the command; (2) no proposed change — skip list cost is
inherent to the chosen structure and the alternative (a mutable B-tree) was
already rejected as a bigger project than the intended one; (3) encode
directly into the WAL's write buffer rather than through an intermediate
`Batch` allocation; (4)/(5) no proposed change — both run only off the
hot serving path, so their cost is amortized over flush size and not worth
trading complexity for.

## Top 5 allocation sites (measured — `heap.prof`, `alloc_space` + `alloc_objects`)

**Hypothesis, written before capture:** the RESP read path and the WAL batch
path would dominate allocation count, because every command allocates at
least one buffer for its arguments and one for its WAL record, and both run
per-operation rather than being amortized.

**Measured**, ranked by `alloc_objects` (the metric that matters for GC
pressure — T8.4 will correlate this against GC pause data):

| Rank | Site | alloc_objects | alloc_space |
|---|---|---|---|
| 1 | `bufio.(*Reader).ReadBytes` (RESP line reads) | 163,842 (22.7%) | 2,560 KB |
| 2 | `memtable.(*SkipList).Insert` | 155,655 (21.5%) | 8,193 KB (17.7%, largest by *space*) |
| 3 | `resp.(*Reader).readBulk` | 90,115 (12.5%) | 4,096 KB |
| 4 | `wal.(*Batch).Encode` | 76,464 (10.6%, 142,000 cumulative) | 6,145 KB |
| 5 | `resp.(*Reader).readArray` | 39,798 (5.5%, 293,755 cumulative — the largest *cumulative* count in the profile, 40.7% of all objects) | 8,706 KB (largest by *flat* space, 18.8%) |

The hypothesis was directionally right — RESP parsing and skip-list insertion
are indeed the two largest sources — but wrong on which dominates: skip list
*insertion* costs more bytes per allocation (8.2 MB for 155k objects, ~53
bytes/alloc, consistent with a multi-level node) than RESP parsing does, but
RESP parsing's `readArray` accounts for the largest share of allocation
*count* once its callees are included (40.7% cumulative), because it is the
single function every command passes through regardless of size. `commandArgs`
and the two `binary.littleEndian.Append*` helpers appear further down
(4.5–5.4% each) — small, fixed-size allocations that are candidates for
`sync.Pool` reuse in T8.3 specifically because their lifetime is one command.

## Worst contention point (measured — `mutex.prof` + `block.prof`)

**Hypothesis, written before capture:** `docs/concurrency.md` and the T8.1
`sync=always` finding already named `memtableSet.Add`'s lock as the
suspected worst contention point, because it is held across the WAL fsync
under `sync=always`; this run used `sync=interval` specifically to check
whether the contention is still visible without the fsync in the critical
section.

**Measured:** confirmed as the worst point, and it is not close. Captured
over a 15-second, 20-client mixed 80/20 run:

* `sync.(*RWMutex).Lock`/`Unlock` inside `memtableSet.Add` accounts for
  **84–97% of all block and mutex profile samples** (196.7s of 233.8s block
  time; 190.2s of 197.1s mutex time, both cumulative). `LSM.Put` →
  `memtableSet.Add` is 78.6% of mutex-wait time on its own; `LSM.Delete` →
  the same lock adds another 18%.
* This confirms the contention persists under `sync=interval`, i.e. it is
  not purely a symptom of holding the lock across an fsync — the lock is a
  single `sync.RWMutex` guarding the entire active memtable, so *every*
  concurrent write serializes on it regardless of sync policy, and
  `sync=always` only makes the held-time-per-acquisition worse.
* Everything else is noise by comparison: `Scheduler.run`
  and `Flusher.run` together account for roughly 10% of block time from
  compaction/flush coordination, an order of magnitude below the memtable
  lock.

**Proposed fix, to be tested in T8.3:** this is a known, already-documented
design tradeoff (`docs/concurrency.md`), not a new finding — the concrete
next step is a benchmark of a sharded memtable (multiple skip lists keyed by
a hash of the user key, merged at read time) against this measured baseline,
specifically because "shard the lock" is the standard answer and this
profile is the evidence that justifies spending the T8.3 budget on it rather
than on something further down the list.

## Reproduction

```
go test ./test/stress -run TestMixedWorkloadStress -count=1 \
  -stress.duration=15s -stress.clients=20 -stress.profile=docs/profiles
# then rename test/stress/docs/profiles/{block,mutex}.prof into docs/profiles/
  (a relative -stress.profile path resolves against the test package's
  working directory, not the repo root -- pass an absolute path to avoid this)

bin/strata-server -addr :6382 -data-dir .bench-data -sync interval \
  -pprof-addr localhost:6061 -log-level error &
bin/loadgen mixed -addr 127.0.0.1:6382 -clients 20 -duration 20s \
  -keyspace 50000 -read-frac 0.8
curl -s http://localhost:6061/debug/pprof/heap -o docs/profiles/heap.prof
```
